# M9.5 Worker Redesign — 1 worker = 1 pod + 预登记 + token 鉴权

> **⚠️ V1 阶段撤回 (2026-08-15)**: 团队技术栈全是 Java, Go worker 维护成本不划算; V1 阶段改 in-process 模拟 (shipyard 后端不调 K8s, simulateWorkerDeploy 5s 后异步 SUCCESS). V5 migration 把 worker 表回滚到 V3 结构, env 表加回 workerUrl / workerTokenEnc / k8sNamespace 3 字段.
> **V1.5+ 真接 worker 时**: 写 V6 migration 升级回 M9.5 结构, git cherry-pick M9.5 commit d029106 + 后续修复, 同时重构 worker 端为 Java (M9.5 当时是 Go, V1.5+ 改 Java).
> **决策留档**: 见 `docs/2026-08-15-decision-go-vs-java.md`.

> **TL;DR**: 仔哥 2026-08-15 拍板, 彻底重构 worker 体系. 旧模型 (2 pod 1 row 共享) 引发 UI 实例数 / 集群代理 4 个不一致问题. 新模型:
> - 1 worker = 1 pod (跟 k8s 一致)
> - Pre-register: 用户在 shipyard UI 创建 worker (预登记), 然后再去 k8s 部署 pod
> - Token 鉴权: shipyard 端生成 token, 存 SHA-256 哈希, 明文只展示一次
> - 状态机: PLANNED → PROVISIONING → ONLINE → OFFLINE/UNHEALTHY

---

## 1. 决策背景

### 1.1 旧模型 (M9 commit-16) 的问题

| 现象 | 根因 |
|---|---|
| UI "实例数 0/0" | 2 pod 共用 1 worker row, 调 worker /api/v1/cluster/worker-pods 拿 replicas, 但跟实际 pod 数对不上 |
| "集群代理测试" 4 个接口全失败 | shipyard 调 worker 走 `worker.workerUrl` 字段, register 时由 `workerName` 写库, 但 register 逻辑选 row 用了 workerUrl 主键, 然后被 shipyard 不允许覆盖, 永远没生效 |
| worker_name 字段在 DB 永远是空 | shipyard register 漏 `w.setWorkerName(req.getWorkerName())`, 后续 SQL 改唯一约束 (env_id, worker_name) 后, 2 pod register 都报 DuplicateKeyException |
| 4 个脏 row 累积 | 旧逻辑 + 新唯一约束 + 2 pod 启动 = DB 出现 4 个不同 workerName 的 row |
| register 没 token 校验 | 任何 worker 用 `WORKER_TOKEN=test-token` 都能 register 到 shipyard, 没有 worker 身份认证 |

### 1.2 仔哥的新思路 (2026-08-15)

> "新建环境的时候可以同时创建多个 worker, 填写 worker 的基本信息, 这样环境创建好之后就直接在 worker 页面看到 worker 的数据, 哪怕还没有真实地把 worker 部署到 k8s 中"

本质: **流程反转** (规划在前, 部署在后)

旧: 用户部署 pod → pod register → shipyard 入库 (被动发现)
新: 用户预登记 worker → shipyard 入库 (status=PLANNED) → 部署 pod → pod register 严格匹配 (env_id, podName) → 状态变 PROVISIONING → 心跳 → ONLINE

## 2. 数据模型

### 2.1 worker 表 (V4__redesign_worker_table.sql)

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | bigint | 主键 (雪花 ID) |
| `env_id` | bigint | 所属环境 (1 env — N worker, 1:N 关系) |
| `name` | varchar(64) | shipyard 内部展示名 (同 env 下唯一) |
| `pod_name` | varchar(128) | k8s pod metadata.name (同 env 下唯一, register 严格匹配) |
| `description` | varchar(256) | 备注 (可选) |
| `worker_url` | varchar(512) | worker 启动后 register 时上报, shipyard 调 worker 用这个 |
| `worker_token_hash` | char(64) | worker 鉴权 token SHA-256 哈希 (Hex 64字符, 不存明文) |
| `status` | varchar(16) | PLANNED / PROVISIONING / ONLINE / OFFLINE / UNHEALTHY |
| `health` | varchar(16) | worker 自检: HEALTHY / UNHEALTHY |
| `health_detail` | varchar(512) | worker 自检失败原因 |
| `last_heartbeat_at` | datetime | 最后心跳时间 (worker 30s 上报一次) |
| `version` | varchar(32) | worker 版本 |
| `created_by` | varchar(64) | 创建人 (V1 默认 'system', V1.5 接用户体系后存 userId/email) |
| `created_at` | datetime | 创建时间 (BaseEntity 自动填) |
| `updated_by` | varchar(64) | 修改人 (register / heartbeat 系统行为用 'system:register' / 'system:heartbeat' 标记) |
| `updated_at` | datetime | 更新时间 (BaseEntity 自动填 + 自动更新) |
| `deleted` | tinyint | 软删: 0=active, 1=deleted |

#### 唯一约束 / 索引

- `UNIQUE (env_id, pod_name)` — 同 env 下 podName 唯一
- `UNIQUE (env_id, name)` — 同 env 下 name 唯一
- `KEY idx_worker_status (env_id, status)` — WorkerSelector 按状态选
- `KEY idx_worker_heartbeat (last_heartbeat_at)` — WorkerHealthScanner 扫超时

### 2.2 env 表删字段 (V4__redesign_worker_table.sql)

- ❌ `worker_url` (移到 worker 表, 每个 worker 自己的)
- ❌ `worker_token_enc` (移到 worker 表, 每个 worker 自己的 token, 哈希存)
- ❌ `k8s_namespace` (worker 表通过 POD_NAMESPACE downward API 拿, env 不再管)

env 表只管集群元数据: `name` / `displayName` / `clusterType` / `isProduction`

### 2.3 状态机

```
                  (用户在 UI 创建)
                        ↓
                    PLANNED    ← 预登记, status 字段 = 'PLANNED', 还没 register
                        ↓ (worker pod 启动, register 找到预登记 row)
                  PROVISIONING  ← token 校验通过, workerUrl 上报
                        ↓ (第一次 heartbeat)
                     ONLINE    ← 心跳新鲜 (90s 内)
                        ↓
                  ┌──────┴──────┐
                  ↓             ↓
              心跳超时 90s   worker 自检失败
                  ↓             ↓
                OFFLINE       UNHEALTHY
                  ↓             ↓ (worker 自检恢复)
                (deleted=1)  ONLINE
                  ↑
                用户在 UI 删除 / k8s pod 永久消失
```

## 4. Register 严格模式流程

```
1. worker pod 启动 (k8s manifest 配 downward API: POD_NAME / POD_IP)
2. worker 端读取 env: POD_NAME / POD_IP / WORKER_TOKEN / SHIPYARD_URL
3. worker 构造 RegisterRequest: { podName, env, workerUrl, workerToken, k8sVersion, nodeName, podIp, version }
4. worker 调 shipyard: POST /api/workers/register
5. shipyard 端:
   a. 查 env_id by env name (查不到 → 404 "环境不存在")
   b. 查 worker by (env_id, pod_name) 严格匹配 (查不到 → 404 "请先在 shipyard UI 创建")
   c. 校验 token SHA-256 (不匹配 → 401 "token 校验失败")
   d. 更新 workerUrl / version / last_heartbeat_at
   e. status: PLANNED → PROVISIONING (首次) / 保持当前状态 (后续 register)
   f. updated_by = 'system:register'
6. shipyard 返 workerId
7. worker 启动 30s 心跳 loop
8. 第一次心跳到达, status → ONLINE
```

## 5. Token 生命周期

```
[用户在 shipyard UI 创建 worker]
    ↓
shipyard 生成 32 字节随机 base64 token (SecureRandom)
    ↓
存 SHA-256 哈希到 worker.worker_token_hash (Hex 64 字符)
    ↓
返明文 token (一次性, 一次性展示 Dialog)
    ↓
用户复制到 k8s manifest 的 WORKER_TOKEN env var
    ↓
worker 启动 register 时携带明文
    ↓
shipyard SHA-256 哈希后跟存库 hash 比对 (constant-time, 防 timing attack)
    ↓
[token 泄漏 / 需要轮换时]
    ↓
用户在 UI 点 "重新生成 token" → POST /api/workers/{id}/regenerate-token
    ↓
shipyard 重新生成 32 字节随机 token + 存新哈希
    ↓
旧 token 立即失效 (在用旧 token 的 worker register / heartbeat 全部失败)
    ↓
用户更新 k8s manifest WORKER_TOKEN + 滚动重启 worker pod
```

## 6. M9.5.1 网络 fix (2026-08-15)

> **仔哥追加的 1 行 patch, 跟 M9.5 redesign 本身无关, 是 PC 端部署踩的网络坑**

**问题**: worker pod 在 calico pod 网络 (192.168.36.x / 192.168.169.x),
跨网段访问物理机 shipyard (192.168.10.29:8080) 时 10s timeout.

**根因**:
- 即使走 socat 跳板 (DaemonSet hostNetwork) + svc DNS 走 Service ClusterIP,
  最终 kube-proxy DNAT 后还是转到物理机 IP:30090
- **calico pod 网络 → 物理网络** 跨网段 TCP 握手能成, 但**回包路径不对**
  (物理机不知道 calico pod IP, 回包丢失) → 10s timeout
- master 本地 curl 物理 IP:30090 200, 是因为 master 本身在物理网络

**修法** (`k8s/dev/worker-deployment.yaml`):
1. `spec.template.spec.hostNetwork: true` — worker pod 共享物理网络, 跟跳板一样
2. `SHIPYARD_URL=http://192.168.91.139:30090` — 直连物理机 IP, 不绕 svc DNS

**副作用 / 限制**:
- ⚠️ 容器端口 8888 绑物理网卡, replicas > 1 跨 node 安全, 同 node 冲突
- ⚠️ 失去 pod 网络隔离, pod 能访问物理机所有端口
- ⚠️ `status.podIP` 变物理机 IP, WORKER_PUBLIC_URL 语义对齐改 192.168.91.139:30080
- ⚠️ V1.5 改回 ClusterIP, shipyard 跟 worker 同集群, 别用 hostNetwork

**完整排障过程 + 反思**: 见 `docs/2026-08-15-network-issue.md`

## 7. V1.5 / 跨地域部署展望

跟用户讨论的 "上海 worker 集群" 场景对齐:

| 场景 | V1 (本机) | V1.5+ (跨地域) |
|---|---|---|
| worker URL | `http://192.168.91.139:30080` (NodePort) | `http://shipyard-worker.svc.cluster.local:8888` (svc DNS, shipyard 在同集群) |
| 网络 | shipyard 跨网段 (192.168.10.x ↔ 192.168.91.x) | 跨 VPC / 跨地域 (走公网 / VPN / mTLS) |
| 跳板 | DaemonSet + socat + hostNetwork (M9.5 已实现) | Cloudflare Tunnel / frp / nginx stream / mTLS |
| token 传输 | V1 demo 明文 env var | k8s Secret 注入 (base64 不是加密但避免明文) |
| 跨集群 shipyard | 1 shipyard instance | 多个 shipyard (按地域), worker 注册到最近的 |

worker 端代码 / shipyard 端代码 / k8s manifest 都按 1 worker = 1 pod 设计,
跨地域扩展时只需要:
1. 改 shipyard URL (DNS / IP)
2. 改 worker URL (svc DNS / tunnel)
3. token 走 k8s Secret

**不用改业务代码**。

## 9. 验证步骤 (V1 demo)

1. 启动 shipyard 后端 (IntelliJ 跑 `mvn spring-boot:run`, Flyway 自动跑 V4 migration)
2. 启动 web 前端 (`pnpm dev`)
3. 浏览器打开 `http://localhost:5179/workers`
4. 点 "创建 worker" 按钮, 选 env = `dev` (已存在), 填 name = `shipyard-worker-dev-1`, podName = `shipyard-worker-dev-1`

6. 复制 token, 更新 k8s manifest 的 WORKER_TOKEN env var

9. 第一次心跳后, status ONLINE
